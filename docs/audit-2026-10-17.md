# Codebase audit, 17 October 2026

A two-axis review of the whole repository, from the root commit (`975db87`, the
milestone-0 scaffold) to `HEAD` (`9ed63a9`), run with the `code-review` skill.
Two independent reviewers worked in parallel so neither coloured the other:

- **Standards:** does the code follow the repo's documented rules? Sources were
  `AGENTS.md` (especially "Rules that always apply" and "Review guidelines"),
  `CLAUDE.md`, `docs/decisions.md`, `docs/product.md`,
  `tests/fixtures/qloo/synthetic/README.md`, and the ruff config in
  `pyproject.toml`. On top of those, a fixed baseline of Fowler code smells,
  reported only as judgement calls.
- **Spec:** does the code implement what milestones 0 to 4 asked for? Sources were
  the milestone list and screen descriptions in `AGENTS.md`, `docs/product.md`
  and `docs/decisions.md`. Milestone 5 is out of scope.

The findings are kept under separate headings on purpose and are not reranked
against each other: a change can pass one axis and fail the other.

## Standards

**Hard violations: none.** Every item on the `AGENTS.md` review checklist was
verified against the tree.

- **Secrets.** Keys are read from the environment only (`app/qloo/exec.py:43`,
  `app/agent/model.py:30`). `.env` and `var/` are ignored. No key appears in
  source, logs, fixtures, templates, static files or model prompts.
- **Qloo data containment.** No real Qloo data in a tracked file. Synthetic
  fixtures use invented UUIDs (`00000000-0000-4000-8…`) and synthetic correlation
  IDs. The cache database lives in the ignored `var/`.
- **Data sent to Qloo.** Only cultural entities and places
  (`app/agent/profile_agent.py:123`, `app/profile.py`). No names, emails or
  identifiers.
- **Test isolation.** Tests use PydanticAI `FunctionModel` (`tests/test_agents.py`)
  and `FakeQloo` (`tests/qloo_fakes.py`). No test reaches Qloo or a model.
- **Qloo access.** Every call goes through `qloo exec` as a subprocess
  (`app/qloo/exec.py:125`). No direct HTTP to the Qloo API. Agent tools wrap
  `QlooClient` as decision #5 requires.
- **Wording.** No claims about individuals or sensitive traits. The hook line is
  built by code (`app/agent/listing_agent.py:424-427`), so the model cannot put
  temperament into it. Bios are checked fact by fact (`app/agent/checks.py:276-305`).
- **Name screen.** `check_name` at `app/agent/checks.py:110-142` applies the
  blocklist, villain and role screens, with the stricter bully-breed branch at
  lines 137 to 141. Lookalike names stay allowed for bully-breed dogs per
  decision #14.
- **README and UI claims.** No "faster adoption", "saves lives or money" or
  "matching" anywhere. The README speaks of accurate listings and a labelled
  experiment.
- **UI separation.** Templates render view models only; no Qloo, agent or cache
  import under `app/ui/`. View models are built in `app/views/build.py`.
- **Envelope handling.** All six statuses are handled (`app/qloo/envelope.py`,
  `app/agent/profile_agent.py:113-144`, `app/custom_location.py:93-104`).
  Retries happen only when `retryable` is true (`app/qloo/exec.py:99-103`).
  `needs_input` is never forced into a match: a typed location shows Qloo's
  candidates as buttons (`app/custom_location.py:93-104`), and a title the agent
  looked up is chosen among the candidates with a stated reason, which the Why
  panel says (decision #14).
- **Model configuration.** Built from the four `AGENT_*` variables
  (`app/agent/model.py:19-38`). Nothing hard-coded.
- **Call spacing.** `reserve_live_slot` claims the next slot inside a single
  `BEGIN IMMEDIATE` transaction (`app/qloo/cache.py:68-86`), so spacing holds
  across processes. Confirmed by a second independent read.
- **Milestone discipline.** No deployment scripts, CI or Devpost text. README
  sections for milestone 5 are marked TODO.
- **Edit and approve.** `missing_cautions` (`app/listing.py:188-191`) blocks an
  approval that drops a bite or guarding statement, per decision #10.

**Ordinary correctness: nothing found.** The `qloo` subprocess's timeouts,
`OSError`, bad JSON and exit codes 1, 2 and 4 are handled (`app/qloo/exec.py:110-128`).
Session state is guarded by a lock and bounded (sessions capped at 500 with a
two-hour TTL, three added animals per visit, photos up to 3 MB and never written
to disk). The per-visitor limiter is a cached singleton (`app/runs.py:56-61`), so
its in-memory hourly window survives between requests.

**One minor correctness finding, from Codex's review of this audit's branch:**
the limiter's per-visitor table (`app/limits.py`) never dropped a visitor's key.
Every check created an entry, including refused ones, and a visitor's timestamps
were pruned only when that visitor came back, so the table grew with every
distinct client address the run endpoint ever saw (a visitor is the client
address, `app/main.py:178-180`). Fixed on the branch
`audit-2026-10-17-fixes`: looking up a visitor no longer creates an entry, and
each recorded start sweeps out every visitor whose last start is over an hour
old, with a test in `tests/test_product.py`.
Background run failures are surfaced on the Working page rather than swallowed
(`app/runs.py:150`). Approval re-checks taken names after submission
(`app/main.py:502-510`).

**Smell baseline: nothing significant.** Judgement calls examined and accepted:

- *Possible Feature Envy* in `app/views/build.py`, which reaches into `Profile`
  and `ListingResult` fields extensively. Accepted: bridging domain objects to
  presentation is what a view builder is for, and moving formatters onto the
  domain types would leak presentation into them.
- *Possible Data Clumps* in `ProfileDeps` (`app/agent/profile_agent.py:30-47`)
  and `ListingDeps` (`app/agent/listing_agent.py:62-73`), each with seven to nine
  fields. Accepted: PydanticAI's dependency dataclass is the framework's pattern.
- *Possible Repeated Switches* on envelope status across the profile agent, the
  listing agent and `custom_location.py`. Accepted: each site needs a different
  recovery (log a note, show candidates, stop).
- *Possible Speculative Generality* in the replaceable-UI seam with one UI
  shipped. Accepted: `AGENTS.md` requires it and `tests/test_ui_contract.py`
  enforces it.

The two longest files are `app/main.py` (about 730 lines) and `app/views/build.py`
(about 685 lines). Both are within reason for the number of screens they serve.

## Spec

### Missing or partial

**Major: the tone setting is missing.** `AGENTS.md` line 243 describes the start
screen as "a grid of the animals, a choice of three preset locations, a tone
setting, and a 'try an example' button". No tone control exists in
`app/ui/classic/templates/start.html`, in `StartView` (`app/views/models.py`), in
the start route, or in the agents' instructions. The word appears nowhere else in
the repo: `docs/product.md` and `docs/decisions.md` do not mention it either.
Rated major rather than critical because the full design in `docs/product.md`
never asked for it, so the brief and the design disagree. Resolution is the
author's call: either add the setting to `StartView`, the form, the listing
agent and the JSON API, or strike the words from `AGENTS.md` and record the
decision in `docs/decisions.md`.

*Resolved on the same day:* the words are struck from `AGENTS.md` and the
reasoning is recorded as decision #15 in `docs/decisions.md`. No tone setting is
built; the refine line covers the case.

### Implemented but diverging

**Venue pins versus venue list.** `AGENTS.md` lines 245 and 327 say "venue pins"
on the map; the result screen lists venues with neighbourhood and address
(`result.html:148-164`) and draws no pins. This is decision #4 in
`docs/decisions.md`: Qloo returns no coordinates, and an external geocoder was
rejected. The decision is recorded, so this is not a defect, but `AGENTS.md`
still carries the old wording in two places and should be brought in line.

*Resolved on the same day:* the result-screen description now says the venues
are a list and points at decision #4; the milestone-2 brief keeps its original
wording with a note that venues became a list.
